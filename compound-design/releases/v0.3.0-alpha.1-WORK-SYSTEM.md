# Compound Design v0.3.0-alpha.1 — Work System

```
Release stage:            candidate
Stable evidence baseline: v0.2.1 (unchanged)
Evidence level:           E1 — deterministic contracts
Runtime uplift:           not measured
Paid model calls:         0
E2 pilot:                 pre-registered, never executed
```

A candidate release exists because the architecture and the behaviour changed, not because anything was shown to work better. Nothing here is evidence of effectiveness.

## Added

**A work system.** Six loop skills — `cd-frame`, `cd-model`, `cd-build`, `cd-verify`, `cd-polish`, `cd-compound` — plus `cd-strategy` and `cd-compound-refresh` around the loop, and `cd-setup` and `cd-handoff` for operations. Each declares when it applies, when it does not, its write authority, whether it may write an artifact at all, its output contract, what it may never do, how it behaves when a dependency is missing, and when it is finished.

**Six specialist agents.** `compound-design` routes; `interface-reviewer`, `motion-reviewer`, `ai-interaction-reviewer`, `evidence-reviewer` and `learning-curator` are dispatched into their own contexts. An agent defines specialism, trigger, non-trigger, tool policy and boundaries, and points at the skill that owns the procedure. Agents are resources: they entered the registry at E0 and reached E1 through agent contract tests covering routing, non-trigger, skill reference, tool policy, absence of a duplicated procedure and absence of a hidden upstream dependency.

**A shared finding contract.** `compound-design/FINDING-CONTRACT.md` gives the four reviewers one shape: `id, scope, severity, confidence, evidence, impact, recommendation, verification_state, source`, a three-level severity ladder, an `observed | inferred | not-verified` distinction, and gates that drop a finding without evidence and impact, drop low-confidence items from the findings list, consolidate by root cause, and refuse taste as defect.

**Durable learning that can be found again.** `compound-design/DISCOVERABILITY-CONTRACT.md` defines addressable frontmatter — including the literal signals that will recur — and a bounded deterministic search. `cd-frame` and `cd-model` must run it before asking anything; `cd-compound` must prove the learning it wrote is retrievable. Proved mechanically against fixtures: a learning captured in one context surfaces for a different later context, superseded documents never surface, and weak matches are dropped rather than padded.

**An installable plugin.** Manifests for Claude Code, Codex and Cursor, in the formats read from the upstream source at its pinned commit, all passing `claude plugin validate --strict`. One canonical implementation under `skills/` and `agents/` that every host reads directly — no mirrored copy, so nothing can drift — and nothing cloned at runtime.

**Configuration.** `.compound-design/config.example.yaml` with six keys that each have a named consumer. Repository layer tracked, local override gitignored and never created by setup, `docs_root` read only from the tracked file and failing closed rather than silently writing to `docs/`.

**Deterministic tooling.** `compound-design/tools/cd.mjs`: `setup-check`, `config`, `discover`, `contracts`, `plugin`, `registry`, `claims`, `selftest`. Zero model, zero network. Forty self-test checks covering configuration precedence and path-traversal rejection, discovery behaviour, agent contract mutations, schema violations and the claim guard in both directions.

**A candidate benchmark lane.** `compound-design/quality/e2/candidate-v0.3/` pre-registers a comparison of the rewritten resource against the released version it replaced, reusing the frozen task set, rubric and decision rules unchanged. Not executed.

## Changed

- The canonical location of every skill moved from `.claude/skills/` to `skills/`, and agents now live at `agents/`. `.claude/` holds only `launch.json`.
- The registry schema gained `publicName`, `status`, `supersedes`, `supersededBy`, `path`, a nullable `cdqi` and prerelease versions — and is now actually executed by `cd:registry`, which is how a long-standing violation of it was found.
- `cd:evals` runs the active v0.3 contract suite. The v0.2 suite, its result artifact and its runner are frozen as legacy evidence and are not re-executed.
- The claim guard matches claims rather than words, so the evidence documents can define the terms they forbid.
- CI gained a `work-system` job and kept its zero-model guarantee, now asserted by two independent self-tests.

## Known unknowns

- Whether any v0.3 resource improves an outcome over no resource, over direct upstream use, or over the v0.2 resource it replaced. The pilot and the candidate lane are pre-registered and unexecuted.
- Whether the discoverability mechanism changes decisions. The retrieval is tested; the effect is not measured.
- Whether the durability bar in `cd-compound` keeps the store small enough to stay useful. Only real use will show that.
- Whether the routing boundaries between the orchestrator and the specialists hold under real work.
- Whether fifteen skills is the right number. Nothing here is evidence that it is.

## Adversarial review before release

Run against the release's own questions. Answers are what they are, not what would be flattering.

| Question | Answer |
| --- | --- |
| Copying the upstream architecture, or understanding it? | Understanding. The converter CLI, the 35-skill catalogue and the "specialists as skill-local prompt assets" choice were all rejected with reasons; the severity ladder was reduced from four levels to three because the fourth never changed a decision. Each call is recorded in the snapshot document. |
| Skills created because they are needed, or to fill a catalogue? | Each of the fifteen has a named consumer. The two thinnest — `cd-build` and `cd-strategy` — earn their place through contract rather than content: Build exists for its write-authority boundary, Strategy for the anchor Frame and Model read. |
| Duplication between an agent and its skill? | Prevented mechanically: agents are capped at 60 lines, must reference their skill, and fail if they contain a three-step numbered procedure. The largest is 50 lines. |
| Any resource that is only an unnecessary wrapper? | `evidence-reviewer` is the closest — it wraps a single skill. It survives on its isolation and tool-policy boundary. If it does not earn that in use, deleting it is the correct outcome. |
| Any new skill that should have been a reference? | `cd-strategy` was the candidate. It kept skill status because it runs an interview with ownership rules, not because it holds a template. |
| Do the specialists have clear boundaries? | Yes, each states when not to use it and routes what it does not own. |
| Hidden runtime dependency on an upstream? | None. Checked by the plugin gate and by the contract suite over every skill and agent. |
| Any legacy identifier still on an active surface? | None. Checked across skills, agents, manifests, configuration, documentation and the site. |
| Any new resource that inherited E1 without earning it? | None. Eighteen resources entered at E0 and were promoted in a separate commit on the strength of the recorded suite artifact. |
| Was any frozen evidence altered? | No. Every frozen file is byte-identical to the branch point, the task digests are unchanged, and the v0.2 suite and its result were not re-executed. |
| Does the plugin really install? | Yes — installed into an isolated home, listed at 0.3.0-alpha.1, all fifteen skills and six agents discovered by the host. |
| Does the small flow stay small? | Every skill states when not to use it and its lightweight tier; the orchestrator starts at the smallest sufficient stage. Whether that holds in practice is unmeasured. |
| Does Compound actually close the loop? | Mechanically, yes: capture writes addressable learning and Frame and Model retrieve it, proved without a model. Whether it improves decisions is not measured. |
| Is there a mechanism to delete bad knowledge? | Yes — `cd-compound-refresh`, whose outcomes include Delete, gated on a quoted witness or explicit confirmation. |
| Did the system get simpler, or just bigger? | **Both, honestly.** The surface grew from six resources to twenty-one. The structure got simpler: one canonical implementation instead of scattered copies, one finding shape instead of four implicit ones, executable configuration instead of assumptions spread through prose, and no runtime dependency on an upstream checkout. Whether twenty-one resources is the right number is exactly the kind of claim this release is not allowed to make. |

Two changes were made as a result. An unused helper in the tooling was removed. And the benchmark's CI guard was found flagging the workflow comment that documents the zero-model guarantee — the same "cannot tell a stated rule from a violation" bug already fixed once in the claim guard, reintroduced in a second guard because the first fix was applied to one place instead of becoming a rule for all of them. It now scans lines rather than whole files, skips comments, requires an actual assignment, and carries mutations in both directions. Recorded as `CD-20260909-012`.

Nothing else was cut, and no finding was resolved by weakening a gate.
